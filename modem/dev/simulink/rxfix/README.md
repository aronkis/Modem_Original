## Where they run

`assemble_jupiter_240k5_byte.m` phase **2.21**, immediately after phase 2.20
(BEATOBS/BEATFIX). The order is load-bearing: W1's freeze is `fixctl` bit 4, and
`fixctl` — plus the `FixCtlDec` block that decodes it — is created by
`beatfix_overlay.m`. `FixCtlDec` decodes bits 4 (`w1Freeze`) and 5 (`sroSign`)
unconditionally and parks each on a Terminator; `rxfix_w1_overlay.m` deletes the
bit-4 Terminator and takes the signal. `patch_hdlworkflow_rxfix.m` runs in phase
0 beside the other workflow patchers and anchors after the beatfix mapping block.

## W1 — ring witness + per-stage valid census

Semantics are `docs/evidence/rxfix/W1_REGMAP.md`; the injector's `rh_w1_census`
module is the bit-layout truth. Eight read-only 32-bit words, all shadowed behind
one freeze level so a host sweep is a coherent snapshot:

```
0x214 w1_wita  {16'b0, occ[5:0], pushPtr[4:0], popPtr[4:0]}
0x218 w1_witb  {push_on_full[15:0], pop_on_empty[15:0]}
0x21C w1_ss    Symbol Synchronizer strobe  (census stage a = the ring push request)
0x220 w1_rh    Rate Handle validOut        (b)
0x224 w1_cfc   Coarse Frequency Compensator validOut (c)
0x228 w1_cs    Carrier Synchronizer validOut         (d)
0x22C w1_pd    Preamble Detector validOut            (e)
0x230 w1_pc    Packet Controller validOut            (f)
```

Three things about the overlay are not obvious and are the ones to preserve:

1. **It lives in `Frequency and Time Synchronizer`, not `Rate Handle`.** Four of
   the six census stages are children of FTS, so at FTS the census is a pure sink;
   in Rate Handle it would close an RH → CFC → CS → PD → PC → RH cycle. This is
   also exactly where the injector instantiates `rh_w1_census`.
2. **`occ` is the registered TRUE occupancy** — `Validate Input Push Pop`'s
   `Delay` block (`Delay_out1`), never a push/pop pointer delta. A delta cannot
   tell occupancy 0 from 32, which is half of why W1 exists.
3. **The MLFB's statement order is cycle-accurate, not natural**: outputs first
   (they are the shadow captured on the *previous* enb beat), then the shadow
   capture from the *pre-increment* counters, then the increments — and every
   increment is written as an explicit wrap, because MATLAB integer arithmetic
   saturates where the RTL wraps.

## STEER — the Rate Handle pop steering, both branches, one netlist

`rxfix_steer_overlay.m` replaces what used to be two build-time netlist variants:

| | EMPTY edge (skip) | FULL edge (extra pop) |
|---|---|---|
| injector `R4B` | yes | no |
| injector `R4D` | yes | yes |
| this overlay, `fixctl` bit 5 = 0 | yes | branch present, inert |
| this overlay, `fixctl` bit 5 = 1 | yes | armed |

```
pop = (popNom & ~skipEn) | (extraEn & validIn & phase==2 & sroSign)
0x234 r4_wit    {locked[31], skips[30:15], opens[14:0]}
0x238 r4_extras {16'b0, extras[15:0]}
0x25C sro_mode  {30'b0, extraArmed[1], sroSign[0]}
```

`rxfix_inject.py`'s `RH_POP_NEW_R4B` / `RH_POP_NEW_R4D` always-blocks are the
semantics of record: a 13-slot window opened by `Packet Controller.endOut`, lock
after 8 such pulses, `occ <= 8` arms the skip and `occ >= 24` the extra, one of
each per window, and the extra only at mod-4 phase 2. Four things about the
overlay are deliberate and are the ones to preserve:

1. **The pop expression is built from primitives OUTSIDE the MLFB.** The block
   emits only the two registered arming levels plus the witnesses. HDL Coder puts
   an input delay-match register on *some* MATLAB Function inputs and not others
   (`BfGridPace.v`: `en_1 <= en`, `c` live; `RxW1Census.v`: `freeze_1 <= freeze`);
   one landing on `popNom` or `validIn` would move the FIFO pop a beat and change
   the data path silently. Outside, the pop keeps the shape the model already
   has (`BfGridPace -> Compare To Constant -> Logical Operator -> FIFO.pop`).
2. **The two long paths are `Delay` blocks, not persistents.** The injector
   registers `pcEndIn` and the occupancy compare on arrival; transcribing those
   *inside* the MLFB would have left two algebraic loops the RTL does not have
   (Packet Controller → Symbol Synchronizer at the FTS graph, `FIFO.w1Occ` → pop
   inside Rate Handle), because a MATLAB Function block is direct-feedthrough and
   a `Delay` is not. Same flop, same position, loop broken by construction.
3. **`sroSign` gates the arm as well as the fire.** Otherwise on `n_p10` /
   `n_m2p5`, where the ring does reach `occ >= 24`, `extraArm` would latch on an
   R4B-configured image and 0x25C would report `extraArmed = 1`.
4. **The statement order inside the MLFB is the RTL's**, not the natural one:
   Verilog non-blocking assignment means the registered decision reads pre-edge
   state, so it is computed first and applied last, and the `pcEnd` window-open
   is written after the skip/extra latches so that it wins.

Gate: `modem/gates/build_sro_rxfix4b.legs` at `FIXCTL=0` (the netlist must
be R4B) and the `J5` rows of `build_sro_rxfix4d.legs` at `FIXCTL=20` (bit 5), on
a model tree:

## R1 — the Preamble Detector realignment FIFO popped by OCCUPANCY

`rxfix_r1_overlay.m`, formerly injector variant `RXFIX_R1`, whose two lines are
the semantics of record:

```
- assign Delay10_out1 = Delay10_reg[49331];
+ assign Delay10_full = FIFO_numEntries == 14'd12333;
+ assign Delay10_out1 = Delay8_out1 & Delay10_full;
```

The realignment FIFO's data delay was the symbol valid delayed **49,332
`enb_1_2_0` ticks**, which equals 12,333 *valids* only while the valid density is
exactly 1-in-4. Each Rate Handle EMPTY-edge event punches a hole in that density,
so for one epoch the delay is 12,332 valids — and Peak Search counts valids on the
undelayed chain while Timing Adjust counts them on the delayed one, so the two
epoch spaces step a symbol apart. Popping on `push & full` pins the delay at
12,333 valids for ever. At exact 1-in-4 density it is the *same beat*, so the
`s = 0` leg is bit-identical to baseline.

**Unconditional**: no `fixctl` bit. The EMPTY-edge role (bit 5 clear) carries R1
too, which is why the `FIXCTL=0` R4B rows are re-scored whenever it changes.

Four things about the overlay are deliberate:

1. **The 49,332-deep `Delay` block is DELETED, not left dangling.** The injected
   kit left `Delay10_reg` in the netlist (dead, pruned by synthesis); in a model
   a 49k-bit shift register HDL Coder still emits is real fabric. That is what
   the spec's "retires the Delay10 shift register" means here.
2. **Its output had TWO loads.** `Delay10_out1` drove the FIFO's `.pop(...)`
   *and* `Delay14` (`Delay14_out1 <= Delay10_out1;`), i.e. Timing Adjust's
   `validIn`. The injector redefines the net so both loads follow; the overlay
   re-drives **every** destination of the deleted line from `PdPopIndex/1`.
   Rewiring only the FIFO starves Timing Adjust and reads as a DSP bug.
3. **The block is found by following the pop line, never by `DelayLength`.** On
   this tree the length is the *expression* `searchSamples * 4`, so
   `find_system(...,'DelayLength','49332')` matches nothing. The length is
   resolved afterwards as a soft confirmation (a warning if the symbol is out of
   scope; identity already rests on the pop line).
4. **`PdPopIndex` is stateless on purpose.** No persistents ⇒ HDL Coder emits a
   pure combinational module with no clk/reset and no input delay-match register
   (`FixCtlDec.v` on this tree is the same shape: five `assign`s). That is what
   makes it safe to route a DATA-PATH signal through a MATLAB Function block here
   where STEER's item 1 deliberately did not. There is no algebraic loop either:
   `numEntries` leaves the FIFO from `Validate Input Push Pop`'s `Delay` and
   neither subsystem is atomic, so Simulink traces the feedthrough through the
   register.

`make_sro_trees.sh --from-regen` re-points the `pdPopReq` tap
(`u_Preamble_Detector.Delay10_out1`, a net that no longer exists on a model tree)
at `PdPopIndex_out1` in `wrap_byte_sro4b.v`, `wrap_byte_sro4d.v` and
`wrap_byte_bs.v`, and asserts it did — `verilator` runs `-Wno-fatal` here, so a
stale hierarchical tap is not guaranteed to fail the build.

Gate: `modem/gates/build_sro_rxfix4dr1.legs` S1-S5 at `FIXCTL=20` plus the
five `R4DR1/n_*` rows, AND a re-run of the five `R4B/n_*` rows at `FIXCTL=0`
(R1 is unconditional, so the EMPTY-edge role carries it):

```

## A constraint every overlay here inherits: keep the beatfix ports LAST

`modem/instruments/ddrcap/ddrcap_inject.py` runs on this model's generated HDL
afterwards (`build_base_tree.sh` stage 4) and anchors its `QPSK_Rx` (:309),
`Receiver` (:378, :395) and `TxRxComposite` (:602) patches on the literal
`beatfix_viol_count,` / `beatfix_viol_latch);` port tail — i.e. on that pair being
the **last two outports** of `QPSK Rx` and `Receiver` and the last two pins of the
`u_QPSK_Rx` / `u_Receiver` instantiations. Appending new composite outports after
them breaks every one of those anchors (measured: `BASE_REGEN_INJECT_FAILED
stage=ddrcap`, "Receiver u_QPSK_Rx instantiation not patched", plus the ddrcap2
follow-on). `rxfix_w1_overlay.m`'s `keep_last` helper moves them back to the end
at each level and asserts they landed there.

The same class of constraint applies one level down:
`modem/instruments/ddrcap2/ddrcap2_inject.py:214` anchors its
`Frequency_and_Time_Synchronizer` patch on
`.beatobsPop(Symbol_Synchronizer_beatobsPop)  // ufix5` being the **last pin** of
the `u_Symbol_Synchronizer` instantiation, so BeatObs's three Symbol
Synchronizer outports must stay last too (measured: `BASE_REGEN_INJECT_FAILED
stage=ddrcap2` naming exactly that anchor).

**Any overlay in this directory that adds an outport to `QPSK Rx`, `Receiver`,
`TxRxComposite` or `Symbol Synchronizer` must re-apply `keep_last` for the
instrument ports above, and re-resolve its own port handles by name afterwards
(the renumber invalidates handles captured before it).** Both failures cost a

## The model tree's W1 words are THREE enb beats late at the composite ports

Measured in the sp3 Task 4 fix round (sim gate `modem/rtl_sim/sim_w1.cpp`, env
`W1_LAG=<depth>`): on a MODEL-generated tree the eight `w1_*` composite outputs
carry the census value **three `enb_1_2_0` beats after** the census computes it.
The sim gate mismatches on 3 of every 4 beats at depth 0, 2 of 4 at depth 1, 1 of
4 at depth 2 and **0 at depth 3** (all eleven compared fields, both stimuli).

The cause is HDL Coder's own output delay-matching, not the overlay (the table row
above is unchanged -- `rxfix_w1_overlay.m` is correct; the offset is introduced
downstream, in the generated composite): every one of
the eight ports is pipelined by a 3-deep register chain in `TxRxComposite.v` --
`reg [31:0] delayMatch43_reg [0:2];` clocked under `if (enb_1_2_0)`, then
`assign w1_wita = delayMatch43_reg[2]`, and identically `delayMatch44..50` for
`w1_witb, w1_ss, w1_rh, w1_cfc, w1_cs, w1_pd, w1_pc`. Every intermediate crossing
is a plain wire (`Frequency_and_Time_Synchronizer.v: assign w1_wita = witA;` and
the same in `QPSK_Rx.v` and `Receiver.v`), so the whole latency is those three
registers. The netlist injector's wrapper tapped `u_QPSK_Rx.w1Bus`, *ahead* of
the delay-match, which is why its gate needed no such offset.

**The shipped instrument is unaffected.** 0x214-0x230 are AXI register reads, not
a per-beat stream; a value three enb beats old is ~200 ns at the 15.36 MHz rail.
The offset matters only to a cycle-accurate per-beat comparison, i.e. to the sim
gate alone. A sim-side fix (follow-up) is to tap
`u_QPSK_Rx.Frequency_and_Time_Synchronizer_w1_wita` and its seven siblings in
`make_sro_trees.sh`'s generated wrapper, which restores a lag-0 comparison.

**Generalisation for Tasks 5-8**: a `delayMatch` chain lands on *any* new
composite-level output, so every later overlay's sim gate will meet the same
offset. Tap the subsystem-internal wire, not the composite port.

## `fixctl` bits 4 and 5 exist only when `QPSK_RXFIX` is set

`beatfix_overlay.m` (phase 2.20) emits `FixCtlDec`'s `w1Freeze` (bit 4) and
`sroSign` (bit 5) outputs, and their `FixCtlDecW1FreezeTerm` /
`FixCtlDecSroSignTerm` Terminators, **only** when `QPSK_RXFIX` is set -- G0 is that
a build without the new env var is byte-identical HDL, and two extra MLFB outputs
are not. Consequences for Tasks 5-8:

* The variable must be set for the WHOLE assemble, not just phase 2.21. BEATFIX
  reads it at 2.20, before any overlay here runs. `modem/fixes/build_base_tree.sh`
  exports it; a hand-run assemble must too.
* An overlay that consumes bit 5 (SRO sign, Task 5) takes over
  `FixCtlDecSroSignTerm` exactly as `rxfix_w1_overlay.m` takes over
  `FixCtlDecW1FreezeTerm`: assert the Terminator, delete its line, delete the
  block, then drive the freed output. If the Terminator is missing, the cause is
  `QPSK_RXFIX` being unset at 2.20 -- say so in the assert.

## BS — the byte-seam census, and PAD — the 191-word padder (task 7)

`rxfix_bs_overlay.m` replaces injector variant `BS` (module `bs_seam_census`),
`rxfix_pad_overlay.m` replaces variant `PAD` (banked twin
`modem/fixes/pad_patch.py`). Layout of record: `modem/fixes/fixes.toml
[fixes.BS]`; bit truth: the injector's module.

```
0x23C bs_words   serializer words emitted (fillers included, post-PAD)   WRAPS
0x240 bs_starts  RxAlign start pulses = frame boundaries                 WRAPS
0x244 bs_push    ByteRxFifo pushes                                       WRAPS
0x248 bs_pop     ByteRxFifo pops                                         WRAPS
0x24C bs_drop    ByteRxFifo drop-oldest events                           WRAPS
0x250 bs_marks   {bs_lasts[31:16], bs_markpush[15:0]}                    WRAPS 52.6 s
0x254 bs_evt     {trunc_last, trunc_min, trunc_max, dropmax}             SATURATE
0x258 bs_cnt     {bs_trunc[31:16], bs_q24[15:8], 8'b0}
freeze = fixctl bit 4 — the SAME level W1 shadows behind, so one host sweep of
0x214–0x258 is a coherent snapshot.
```

### The precondition this task had to settle: `ByteRxFifo` is not model output

The shipped FIFO is the hand-authored 4096-deep BRAM drop-in
`modem/common/rxfifo/ByteRxFifo.v`, installed over HDL Coder's 64-deep register
FIFO by `modem/common/rxfifo/rxfifo_inject.sh` — now stage **`[4a/5] rxfifo`** of
`modem/fixes/build_base_tree.sh`, before `txcap`/`ddrcap`/`ddrcap2`. Ruling and
follow-up: `docs/evidence/sp3/BYTERXFIFO_DROPIN.md`. It is a **tracked design
source**, not an instrument, and does **not** die with the injectors.

Consequence for this overlay: the injector taps the drop-in's internal
`push`/`pop`/`drop` wires by patching that file; a model overlay only sees the
module's **ports** (`clk reset enb word tog wLast wFirst ready outWord valid
outLast outFirst ovf`), and **`ovf` is not a drop pulse** — in v5 it is the
handshake DEBUG word on 0x1B0 whose only drop information is the sticky bit 16.
So the three events are re-derived with the drop-in's own rules:

| event | drop-in (internal) | overlay (ports) |
|---|---|---|
| push | `tog != prev` | XOR edge of `tog`, base rate |
| pop | `valid_i && ready_1`, `ready_1 = delayMatch_reg[3]` | `valid && ready_1`, where `ready_1` is HDL Coder's OWN balanced copy of the raw `byte_rx_ready` MLFB input (see item 2) |
| drop | `push && (wr_p1 == rd_after_pop)` | occupancy shadow: `drop = push && ((occ - pop) == 4095)`, `occ += push - pop - drop` (mod 4096) |

Exact **given** exact push/pop — but a model of the FIFO, not a tap of it, so
`bs_drop == 0` on its own is a shadow agreeing with itself. The gate therefore
also prints `BS_FIFO_WITNESS ovfcnt=…` from a hierarchical tap of the drop-in's
own saturating counter (`make_sro_trees.sh`), and on silicon the independent
witness is 0x1B0 bit 16.

### Five things about the overlay that are deliberate

1. **It is TWO blocks, because a Simulink block has ONE rate.** The injector's
   census is one always block with two clock ENABLES — serializer counters on
   `enbSer` (15.36 MHz), FIFO counters on `enbFifo` (30.72 MHz). A base-rate
   block reading the half-rate serializer sees every `wv` for two base beats and
   would count every word twice. So `BsSerCensus` runs at the serializer rate
   (words, starts, lasts, trunc, the three order statistics, q24) and
   `BsSeamCensus` at the base rate (push, pop, drop, markpush, dropmax, **plus
   the packing and the freeze shadow of all eight words**, so a frozen sweep is
   still coherent to one clk edge). The five serializer-side quantities cross
   slow→fast through explicit `RateTransition` blocks as **values, not events**,
   which is what makes the crossing unable to alias a count.
2. **`ready_1` is HDL Coder's OWN balanced copy of the raw input, not an
   overlay-built `Delay` block — round 2, fixing a round-1 defect.** Round 1 put
   a 4-deep `Delay` block outside the MLFB to reproduce the drop-in's `ready_1`
   (the `rxfix_steer_overlay.m` "keep the long path outside the block"
   reasoning), and fed that into the block as `readyD4`. But **HDL Coder's delay
   balancing counts only pipeline it inserts itself, never a design `Delay`**:
   it balanced the block's other raw input (`fixctl`) against the block's
   longest path with its own 4-deep `delayMatch1_reg`, and did the same to the
   already-delayed `readyD4` input, so the generated `pop` computed
   `valid(k) && ready(k-8)` against the FIFO's real `valid(k) && ready(k-4)` —
   invisible to every scored leg because on a quiescent run pops track pushes
   one-for-one regardless of the offset. The fix feeds `byte_rx_ready` into the
   MLFB **raw** and lets the balancer supply the four beats itself, which is
   where the drop-in's own `ready_1` comes from in the first place: the
   generated `BsSeamCensus.v` now carries `reg [3:0] delayMatch_reg;
   delayMatch_reg[0] <= ready` (under `enb`), `assign ready_1 =
   delayMatch_reg[3]`, `pop = valid && ready_1` — width for width and enable
   for enable the chain the drop-in's `ByteRxFifo.v` itself carries. **General
   rule: to reproduce a generated module's own `delayMatch` chain, feed the
   signal in raw and let the balancer supply it — do not build the chain by
   hand.** Consequence: `delayMatch_reg` (and the sibling `delayMatch1_reg` the
   balancer adds on `fixctl`) is 4 deep, so for up to 4 `enb` beats after reset
   `ready_1` is still draining the register's reset value rather than a real
   historical sample — a startup-skew window, not a steady-state error, and the
   same transient the drop-in has on its own `ready_1`.
3. **The freeze comes from the composite `fixctl` port, not `FixCtlDec`.**
   `FixCtlDec` is in `Receiver/QPSK Rx` and W1 already owns its `w1Freeze`
   output; carrying that bit back *up* would cost two more outports at two
   levels and two more `keep_last` dances to deliver a bit that is already an
   input here. Same BIT (fixctl bit 4), decoded at different hierarchy levels.
4. **The serializer taps are POST-PAD.** The injector's `assign bsWv = wv;`
   reads the module-scope reg *after* `RXFIX_PAD` has rewritten `w/wv/wl` in
   place, so `bs_words` counts fillers — the only way `words191_k1536`'s 79,760
   words for 418 frames is reachable. The chart edit puts the taps immediately
   above the `if wv` block and leaves a marker comment that PAD anchors its
   arbiter **above**.
5. **One level, one `keep_last`.** `ByteSerializer` and `ByteRxFifo` are both
   children of the composite, so unlike W1/STEER there is no carry chain — but
   the eight new composite outports still need the beatfix pair moved back to
   last (`README` section "keep the beatfix ports LAST").

### PAD

Unconditional, no `fixctl` bit. A `start` with 1..190 words accumulated schedules
`191 - wordCnt` all-zero fillers so the stream stays 191-word aligned; real words
completing meanwhile are queued (at most three: one per 64 bits against ≤ 190
filler beats) and released in order. `wordLast` rides the last filler, so
`wordFirst` lands on the new frame's word 0 exactly as at a clean boundary — one
lost frame (no magic → host CRC fails) instead of the three an
`axi_dmac` `SYNC_TRANSFER_START` misalignment costs.

It is a **script edit to the `ByteSerializer` chart**, inserted between the core
`qpskByteSerializer` call and the `if wv` block that drives `tog`/`heldWord` —
that position *is* the semantics, because the arbiter rewrites `w/wv/wl` in
place. Its persistents join the existing `persistent` line and the existing
`isempty` init block (the injector puts its resets in the serializer's own reset
branch), and the queue is three scalars rather than an array so HDL Coder cannot
decide to map it to RAM. It requires BS to have run and asserts the marker by
name. It surfaces nothing, so like TXF3 it needs no `keep_last`.

## TXF3 — the transmitter's 120.2 s stall fix (F1+F2+F3), task 8

`txfix_f3_overlay.m` is the one file here that fixes the **transmitter**. It
replaces `modem/fixes/txfix_inject.py` variant `F3` (= F1 + F2 + F3, the shipped
variant; `fixes.toml [chain].txfix.variant = "F3"`). It runs **last** in phase
2.21, after the RX overlays — it reads and edits only
`Transmitter/QPSK Tx/Bit Packetizer`, so the order is a courtesy to them, not a
dependency.

**Two env gates, and both must be set: `QPSK_RXFIX` *and* `QPSK_TXFIX`.** Every
other overlay here rides `QPSK_RXFIX` alone; this one has a second gate because
four rows of its own gate matrix (G3, G4/G5 k0+k6, G7) compare a **capture** from
the tree under test against the unfixed baseline `beat_runs/g0_none_U`. With one
shared gate there is no way to express "this receiver, stock transmitter", so the
only available baseline came from the injected lineage — a receiver with no RX
overlays at all — and those four rows measured the receiver, not the fix (sp3
task 8 fix rounds 1-2; `docs/evidence/sp3/TXFIX_F3_GATE.md` §5). The combinations:

| `QPSK_RXFIX` | `QPSK_TXFIX` | result |
|---|---|---|
| 1 | 1 | the normal regen — RX overlays + the TX fix. `build_base_tree.sh` exports both |
| 1 | *empty* | the **model-lineage unfixed TX baseline**: same receiver, stock transmitter |
| unset | any | no overlay at all (byte-identical HDL to a stock build) |

`modem/fixes/build_base_tree.sh` exports `QPSK_TXFIX="${QPSK_TXFIX-1}"` — the `-`
form, so a caller's **empty** value survives (`:-` would substitute the default
and silently rebuild the fixed tree):

```
QPSK_TXFIX= modem/fixes/build_base_tree.sh <dest_parent>     # the U baseline
```

| injector patcher | file it patched | what the overlay does instead |
|---|---|---|
| `patch_data_bits_fifo` (F1) | `Data_Bits_FIFO.v` | `TxF1BoundaryGuard` (AND) between `Compare To Constant1` and the latch's **reset** input |
| `patch_ram_frame_status_indicator` (F2) | `RAM_Frame_Status_Indicator.v` | script edit of the existing MLFB: saturating `frameCount` |
| `patch_bit_packetizer` (F3) | `Bit_Packetizer.v` | `TxF3ReadyGate` (AND) of `DataReadyPaceCmp` with `Logical Operator2` (= `~fullRAM`) |
| `patch_matlab_function1` (F3) | `MATLAB_Function1.v` | script edit of the existing MLFB: saturating uint16 `count` |

**It surfaces nothing** — no new outport at any level, no AXI register, so
unlike every RX overlay here it needs **no `keep_last`** and cannot be the cause
of a `BASE_REGEN_INJECT_FAILED`.

Four things are deliberate and are the ones to preserve:

1. **F1 is an AND on the latch's RESET input, and the equivalence is
   unconditional.** The generated `Unit Delay Enabled Resettable Synchronous`
   emits `if (C1) out <= 0; else if (C3) out <= C2;` — reset beats enable, so the
   pop-enable latch is cleared *mid-frame*. Feeding it `C1 & C3` reproduces the
   injector's `DBF_NEW` on all four `(C3,C1)` combinations **without** relying on
   the `C2 === ~C1` identity the injector's comment leans on. The port order
   (1 data, 2 enable, 3 reset) is asserted by the identity of the block driving
   each input, never assumed.
2. **The two saturating counters are SCRIPT EDITS, not new blocks.** `RAM Frame
   Status Indicator` and `MATLAB Function1` are already MATLAB Function blocks;
   the brief's `FrameCountSat` replacement block would rename the module and the
   instance, and both TX gate harnesses (`sim_txfix_force.cpp`,
   `txrate_probe.cpp`) *read and force* `…u_RAM_Frame_Status_Indicator.frameCount`
   and `…u_MATLAB_Function1.count` by hierarchical path. Those expand to C++ *member*
   paths, so a rename is LOUD — the harness stops compiling and G9/G10/G11/G12 are
   unrunnable until the paths are re-derived — but it costs a rebuild of the whole
   gate chain for no gain.
3. **The saturation limits are literals (3, 65535), as in the injector** (`2'b11`,
   `16'hFFFF`). They are the full range of the two `fi` types, which follow from
   `dataBitsPerPacket` (24640 at the deployed rung → `depth` 49279 →
   `nextpow2` 16). `nextpow2` is *not* re-evaluated in the always-executed body;
   the guarantee comes from the exact-text anchors plus a post-regen grep for
   `reg [15:0] count` / `reg [1:0] frameCount`.
4. **Three block names in this subsystem contain NEWLINES** — `Compare\nTo
   Constant3`, `Logical\nOperator2`, `Unit Delay Enabled Resettable\nSynchronous`.
   Exact-`Name` `find_system` reports them as missing anchors; the overlay's
   `one()` helper matches with `'regexp','on'` and asserts exactly one hit.

F3b (`--margin`, fullRAM threshold 49279 → 49263) is **not** applied. The overlay
refuses a chart that already carries it, and does so in the chart's own idiom: F3b's
threshold change appears there as `full = (count > depth - 16);`, not as the
injector's `16'b1100000001101111` Verilog literal (a literal that can never occur in
a MATLAB script — an earlier revision grepped for it, which was dead code reading as
a refusal). The stock `full = (count > depth);` is asserted verbatim, and because
`TXFIX_F3` is a **prefix of** `TXFIX_F3B`, the F3b marker is tested *first* — the
hazard `txfix_inject.py:patch_matlab_function1`'s own docstring is written about.

### Gate (TX matrix)

```

then the eight `|F3|` rows of `evidence/txfix_gate_runs.txt` and
`txfix_gate_score.py` (which also derives G13 from G11's log and reruns the G14
lint). Pass = every row that PASSes on the injected tree PASSes on the model

Two traps recorded there and worth repeating: `txfix_gate_launch.sh` cannot be
used (it needs `ops/agents/`, which the 2026-09 cleanup removed), and
`txfix_gate_score.py` keys completion on a `TXFIX_GATE_RUN_EXIT` trailer in
`beat_runs/txfix_gate_<id>_<prefix>.log` under the **manifest's** out-prefix — so
the two passes reuse the same prefixes and every artefact of pass A must be moved
aside before pass B runs, or a pass-B run that fails to start scores pass A's
data as a model-tree PASS.

A model tree also carries **DDRCAP-v2** records, whose frame mark is bit 14 of lane 2
rather than v1's `lane2 == 0x7FFF`. `kick_seq.py:frame_marks` and
`txfix_gate_score.py:aligned_content_check` accept both (v1 first, so an injected tree
scores through the identical path), and `offsets_clean` treats an **empty** offset list
as not-clean instead of vacuously true. The scorer also falls back to the tracked
`evidence/txfix_gate_runs.txt` when no manifest sits beside it.

`tree_marker.sh <tree> F3` reports `model` for such a tree, but note its model
check is only `grep -q fullRAM Bit_Packetizer.v`, which the **unpatched** file
already satisfies (`wire Data_Bits_FIFO_fullRAM`). The real post-check is the
`dataReady` assign itself.
