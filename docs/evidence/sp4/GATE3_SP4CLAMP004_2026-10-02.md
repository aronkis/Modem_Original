## 2. The afternoon it cost, 11:36 .. 15:50

* My chain script logged `gate3 rc=1` and went on to re-arm the trigger instead of rolling 148 back: 148 on an
  f3072 image, 146 on f1536, no link, and the delivery sentinel ran a WEDGE recovery bring-up every ~10 min for
  2.5 h (`sentinel.log` 11:36-14:40).
* Restore attempt 1 (14:08) polled `/dev/shm/RIG_LOCK`, read "clear", and every board access was refused -- the rig
  mutex is `~/modem-status/RIG_LOCK` (`ops/sim_repro/riglock.sh`) and the sentinel's bring-up held it.
* Restore attempt 2 (14:37) flashed 148 back to 8503f226395c, but the r3 bring-up failed its settle (148 1093 f/s) and
  both daemons then died at start: `F1536 mode needs the 2 MB carve layout -- rebuild with -DQPSK_CARVE_2MB`. The r4
  rail's `restore_known_good` had re-provisioned `qpsk_tun` as the 4 MB-carve build on both boards (`strings
  qpsk_tun | grep QPSK_CARVE_` = `QPSK_CARVE_4MB`); an image-only rollback cannot run f1536 on it. Watchdogs
  relaunched the daemon every 10 s.
* `gate3_pair.sh --rollback-only` (15:07-15:21) did it properly: images to the CURRENT roles, `restore_known_good.sh`
  at r3 (host app rebuilt `QPSK_CARVE_2MB`, ARM GATE PASS try 4, watchdogs up, health 146/148 fsync 1269/1263,
  0 resets) -- **but** it inherited `SRO_SIGN_CONF=sro_sign.r4.conf` (both boards 1) from the r4 gate's environment
  and wrote R4D steering on 148 (`0x25C=1`; 148 then read crc 83-90 %, estimate −11155, 135 resets). A plain r3
  bring-up with the environment cleared (`env -u SRO_SIGN_CONF bringup_r2r3.sh r3`, unit `plainbringup-154910`)
  restored 148's R4B steering.

The dtbs stay at the 4 MB carve on both boards (f1536 / 2 MB host builds run on it, `docs/setup-prebuilt.rst`).

## 3. Lessons (recorded in memory; rail fixes in this PR)

1. **A chain must roll 148 back itself when `gate3_pair.sh` returns non-zero after the 148 flash** -- and the rail
   should do it: the 146-failure branch now runs the same rollback step [9] before exiting 1.
2. The rig mutex is **`~/modem-status/RIG_LOCK`**; wait on it and on `pgrep -f "bringup_r2r3|restore_known_good"`.
3. **A rung change re-provisions the host build.** Cross-rung rollback = `gate3_pair.sh --rollback-only`, never a
   bare `deploy_image.sh`.
4. The rollback's `restore_known_good` must run with the **rollback rung's** steering conf: step [9] now drops the
   candidate rung's `SRO_SIGN_CONF` from the environment.

## 4. What next for r4

The failure is specific: with both boards on sp4clamp004 at the 2.1/1.9 r4 plan, 148 detected nothing while 146
received 885 f/s. Before another pair gate, test 148's receiver at r4 in isolation -- the r4 forward plan
(148 RX 2100060000 against 146 TX 2100000000; the +60 kHz offset was measured at 2.0 GHz, `test_rung_table.py`
"the cell that measured 99.84 % CRC") and the 4 MB host build on 148 (`qpsk_tun -G3 -r 30720`) -- e.g. the one-way
pair at r4 (`oneway_bringup.sh`) or a 146-TX-only / 148-RX-only cell, and a 148 mode-1 loopback at r4 is already
known good (ARM_OK above). The sp4b run of 09-24 brought the r4 pair up at the old 2.0 GHz plan; today's is the
first r4 pair bring-up on the 2.1 GHz forward carrier.
